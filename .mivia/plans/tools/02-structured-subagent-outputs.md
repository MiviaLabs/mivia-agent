# tools/02 - Structured, schema-validated subagent outputs

**Status:** DESIGN
**Date:** 2026-08-02
**Depends on:** plan `47` (subagent output by reference) for envelope shape;
none hard.
**Blast radius:** MEDIUM-HIGH - subagent loop termination, skills contract,
agent definitions, parent consumption patterns.

## 1. Problem

`skills.Definition` declares `InputSchema`/`OutputSchema`
(`internal/skills/skills.go:25`) and **no non-test code reads either field**
- they are dead. Subagent replies are free prose in a fixed envelope
(`buildResult` in `internal/subagents/multi_step.go`); nothing validates
shape, so parents cannot consume results programmatically and routinely
re-read the same files the child already read. `modelVisibleOutput` passes
bytes through as JSON-if-valid with no contract.

## 2. Goal

A task may demand a schema; the subagent's final output is validated against
it before the run counts as completed, with bounded retry-on-violation inside
the child loop (where the retry is cheap) instead of at the parent (where it
costs a whole dispatch).

## 3. Design

### 3.1 Schema sources, in precedence order

1. `Task.OutputSchema` - new optional field on the dispatch/spawn task shape
   (JSON Schema object, size-capped, validated at task admission).
2. Active skill's `OutputSchema` - finally reading the dead field.
3. Agent definition default (optional `output_schema` in agent TOML).
4. None -> today's free-text behavior, unchanged.

`InputSchema` symmetrically validates `Task.Input` at admission: a malformed
input fails fast at `dispatch_tasks` argument time, before any spawn cost.

### 3.2 Enforcement point: inside the child loop

On the subagent's final step (no tool calls pending), the handler validates
the candidate output:

- Valid -> `buildResult` embeds parsed output under `output` (object, not
  string) plus `schema: "ok"`.
- Invalid -> inject a bounded corrective tool-role message ("output failed
  schema validation: <first N errors>") and allow up to
  `schema_retry_max` (default 2) additional model steps, within the existing
  wall-clock/step budgets - never extending them.
- Exhausted -> result status `failed`, reason `schema_violation`, with the
  last candidate under `output_ref` (never inline - it is known-malformed)
  so the parent can inspect without trusting it.

Validation uses one shared JSON Schema validator; the hand-rolled
`validateSchema` in `internal/tools` is for tool args and stays separate,
but pick a library usable by both so min/max/enum semantics do not diverge.

### 3.3 Parent-side contract

- Result envelope gains `schema: ok|violation|none`. With plan `47`, a
  schema-valid structured output below the inline threshold is inlined as an
  object the parent can consume directly - this is the token win: findings
  as data (paths, line numbers, verdicts) instead of prose the parent
  re-verifies by re-reading files.
- Prompt guidance: the task prompt automatically appends a bounded
  "return JSON matching this schema" instruction derived from the schema -
  generated by the host, deterministic, never echoing task content.

### 3.4 Bounds

- Schema size cap (e.g. 16 KiB), max depth, no remote `$ref` resolution
  (fail closed at admission).
- Corrective messages bounded (first 5 errors, 1 KiB) - schema errors can
  quote model output, so they pass process redaction before injection.

## 4. Invariants

- No schema -> byte-for-byte today's behavior.
- Retry steps never exceed existing step/wall-clock budgets.
- A `completed` status with `schema: ok` guarantees the parsed object
  validates - parents may consume without re-checking.
- Malformed output is never inlined into the parent transcript.
- Fingerprint/idempotency (`requestFingerprint`) covers `OutputSchema` so a
  schema change is a different run.

## 5. Steps

1. Admission validation of `Task.Input`/`Task.OutputSchema` + size caps.
2. Validator selection (one library, shared semantics), wrapper package.
3. Child-loop final-step validation + bounded retry + failure reason.
4. Envelope `schema` field; plan-`47` inline-object path.
5. Read `skills.Definition.InputSchema/OutputSchema`; agent TOML default.
6. Docs: schema authoring guidance for skill/agent authors.

## 6. Testing

- Matrix: no schema / valid first try / valid after retry / exhausted /
  schema itself invalid at admission.
- Budget: retries cannot exceed step or wall-clock ceilings.
- Idempotency: same task ± schema -> different fingerprints.
- End-to-end: parent dispatches with schema, consumes `output.files[]`
  without any re-read tool calls (assert on the parent's tool-call trace).

## 7. Failure analysis

- Models pad JSON with prose fences: strip a single well-formed code fence
  before validation (deterministic, tested) - nothing looser.
- Schema too strict -> chronic exhaustion: `schema_violation` reason is
  distinct and countable in run events; authors see it immediately.
- Injection via schema error text: bounded, redacted, and framed as tool-role
  correction - never executed as instructions.
