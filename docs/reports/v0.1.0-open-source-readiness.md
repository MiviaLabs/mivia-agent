Scope: public source release and binary version 0.1.0

## Summary

Mivia compiles, but it is not ready for a public release.

Do not make the repository public yet. Do not create the `v0.1.0` tag yet.
The workflow implementation is still in progress. Its completion will not resolve
the other release blockers in this report.

## Critical Security Blockers

### 1. A cloned repository can execute code without user consent

Project hooks load from `.mivia/mivia.toml` automatically. The hook runner
executes them with the full process environment.

Evidence:

- `internal/config/hooks_scope.go:73-142` loads project hook configuration.
- `internal/hooks/exec.go:204-220` executes the configured program.
- `internal/hooks/exec.go:287-306` adds the full process environment.
- Hook integration tests confirm that project hooks run without confirmation.

Reachable path:

1. A user clones an untrusted repository.
2. The repository contains a project lifecycle hook.
3. The user starts `mivia chat` in that repository.
4. The model makes a matching tool call.
5. Mivia executes the project hook with the user's environment.

Impact:

- The hook can execute arbitrary code.
- The hook can read provider keys and other environment secrets.

Required change:

- Require explicit project-hook trust.
- Bind trust to a content digest.
- Pass only an allowed environment set to project hooks.
- Add negative tests for an untrusted project hook.

### 2. A project configuration can send a provider key to an attacker endpoint

The project configuration has priority over the user configuration. It controls
`base_url` and `api_key_env`. The provider sends the selected key as a bearer token.

Evidence:

- `internal/config/paths.go:50-62` gives the project file priority.
- `internal/config/load.go:51-60` reads the selected key from the environment.
- `internal/config/load.go:88-101` stores the project endpoint and key.
- `internal/provider/openai_compat_request.go:25` selects the request endpoint.
- `internal/provider/openai_compat_request.go:96-99` adds the bearer token.
- `docs/security/overview.md:97-112` records this behavior as an accepted exposure.

Reachable path:

1. A user clones an untrusted repository.
2. The project config names an environment variable that the user has set.
3. The config points `base_url` at an attacker HTTPS endpoint.
4. The user starts a chat request.
5. Mivia sends the selected key to that endpoint.

Impact:

- An attacker can steal a provider credential.

Required change:

- Give user-owned configuration authority over provider endpoints.
- Give user-owned configuration authority over credential routing.
- Require explicit trust before a project can change either value.

## Publication Blockers

### 3. The license is inconsistent

`README.md:3` and `README.md:268-270` say MIT. `LICENSE:1-17` says
Apache-2.0, but it contains only the short notice.

Choose one license. If the project uses Apache-2.0, include the complete license
text. The Apache Software Foundation guidance requires the full text in the
top-level `LICENSE` file.

Reference: <https://www.apache.org/legal/apply-license>

### 4. There is no working first-run path

The CLI has no `init` command. `mivia init` returns `unknown command`.

A clean installation with only `DEEPSEEK_API_KEY` also fails. Configuration
loading requires a non-empty model catalog. This behavior conflicts with the
key-only quick start in `README.md:38-51`.

Evidence:

- `internal/cli/root.go:15-38` has no `init` command.
- `internal/config/load.go:180-183` rejects an empty model catalog.
- `docs/product/config.md:158-164` says there is no config initialization command.

### 5. There is no release pipeline or correct version injection

The continuous integration workflow has no tag or release job. The Makefile
injects the commit and dirty state, but it does not inject `Version`.

Evidence:

- `.github/workflows/ci.yml:3-29` runs branch and pull-request checks only.
- `Makefile:15-18` injects only `Commit` and `Dirty`.
- `internal/version/version.go:6-8` defaults to `0.0.0-dev`.
- A locally built binary reported `mivia 0.0.0-dev`.

Add a tag-based release pipeline. Build archives, inject the version, publish
SHA-256 checksums, and attach license files. Verify `mivia version` from each
archive.

References:

- <https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases>
- <https://go.dev/doc/modules/publishing>

### 6. There is no end-user installer

`scripts/install_git_hooks.sh` installs development Git hooks. It does not install
Mivia.

Add a Unix `install.sh` with these properties:

- Detect the operating system and architecture.
- Download a tagged release archive.
- Verify its SHA-256 checksum.
- Install the binary atomically.
- Avoid `sudo` by default.
- Support `MIVIA_INSTALL_DIR`.
- Default to `$HOME/.local/bin`.
- Run `mivia version` after installation.
- Include `LICENSE` and third-party notices.

Add a PowerShell installer if Mivia supports Windows.

### 7. Workflow execution is not present yet

The current workflow command supports `list`, `show`, `validate`, and `explain`.
It has no run or resume command.

Version 0.1.0 needs end-to-end tests for these paths:

- A successful workflow run.
- Crash recovery and resume.
- A failed verifier.
- Human rejection.
- Publication denial without explicit authority.
- An empty or unchanged worktree.

### 8. Public documentation contains false provider claims

The README says Mivia supports any OpenAI-compatible provider. The registry
accepts only DeepSeek, OpenRouter, and ZAI.

Evidence:

- `README.md:189-237` documents OpenAI, xAI, and Kimi examples.
- `internal/providerregistry/registry.go:17-30` registers three providers.
- The documented OpenAI configuration returns `unknown provider "openai"`.

Implement a generic OpenAI-compatible provider. Otherwise, remove the unsupported
examples and narrow the product claim.

### 9. Public-tree cleanup is incomplete

The tracked `.claude/settings.local.json` file contains personal absolute paths.
Remove the file and ignore local adapter settings.

Review `.mivia/reports/` and `.mivia/plans/` before publication. These paths
contain pre-launch details and accepted security gaps.

Run a full Git-history secret scan. The completed secret scan covered only the
tracked tree.

### 10. There is no vulnerability-reporting policy

Add `SECURITY.md`. State the supported versions and private reporting process.
Enable GitHub private vulnerability reporting.

Reference:
<https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/add-security-policy>

## Required `mivia init` Contract

Use this minimum contract for version 0.1.0:

- `mivia init` creates user configuration at `~/.mivia/mivia.toml`.
- It does not overwrite an existing file without an explicit option.
- It uses an atomic write.
- It does not accept a secret through command-line arguments.
- It creates no hooks or agent prompts by default.
- It selects only registered providers and models.
- It finishes with the same checks as `mivia doctor`.
- A separate `--workspace` option creates project files.
- Workspace initialization does not change provider authority silently.
- Repeated execution is safe.

Add clean-home, existing-file, permission, non-interactive, and idempotency tests.
