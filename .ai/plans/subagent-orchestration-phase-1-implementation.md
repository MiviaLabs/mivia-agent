## Goal

Build the first vertical slice of subagent orchestration around a repository-pattern ledger. The orchestration layer depends on a ledger interface, not a concrete storage engine. The built-in default is an in-memory repository for local operation and deterministic tests; future repositories may persist to SQLite, another embedded store, or an external data source without changing coordinator behavior.

Phase 1 provides live in-process state only. It must not claim crash recovery, restart resume, multi-process leases, or durable side-effect replay.

## Current source constraints

- `internal/storage/store.go` already defines a low-level append/read event `Store`, plus `Memory` and `SQLite` implementations.
- `internal/storage/queue.go` provides bounded serialized writes through `QueuedWriter`.
- `internal/subagents/subagents.go` owns dependency validation and bounded execution, but state exists only during `Pool.Run`.
- `internal/runtime/dispatcher.go` has transient invocation metadata and event emission, but no queryable run/task ledger.
- `internal/cli/delegate.go` and `internal/cli/dispatch.go` synchronously execute work and expose no run handle.
- Existing storage tests cover storage behavior; existing subagent tests cover scheduling, cancellation, timeout, and dependency behavior. Neither proves a repository-backed live orchestration ledger.

## Architecture contract

```text
model-facing tools / future API
        -> orchestration Coordinator
        -> LedgerRepository interface
        -> MemoryLedgerRepository (default)
        -> adapter boundary for SQLite / other sources
```

The coordinator owns orchestration policy and state transitions. The repository owns persistence and retrieval. The repository must not execute agents, call providers, enforce prompts, or decide protected-action authorization.

### Required identity

Every run/task/attempt receives a system-generated immutable identifier:

- `RunID`: one root orchestration invocation.
- `TaskID`: one logical DAG node within a run.
- `AttemptID`: one execution attempt for a task.
- `ParentTaskID`: lineage within the run; empty only for root tasks.
- `DisplayName`: unique human-readable name scoped to the run, generated by the coordinator.

Caller-provided labels are optional aliases only. They cannot replace IDs, grant authorization, or attach a task to another run.

### Repository interface requirements

Define a narrow `LedgerRepository` interface in the orchestration/storage boundary. The exact package must follow dependency direction. It must support:

- create/get run snapshots;
- create/get task snapshots by `RunID` and `TaskID`;
- append lifecycle events with an idempotency key and monotonic sequence;
- list/query bounded live snapshots by run and status;
- compare-and-set task/attempt transitions so late workers cannot overwrite newer state;
- store bounded redacted output/artifact references, not raw prompts or hidden reasoning;
- close/delete a run only through an explicit lifecycle operation.

Methods accept `context.Context`, return typed duplicate/not-found/invalid-transition/conflict/closed errors, and return defensive copies. The interface must not expose SQL, file paths, provider clients, goroutines, or concrete database types.

### Default and future data sources

- `MemoryLedgerRepository` is the default source for this slice. It must be concurrency-safe, deterministic, bounded by policy, and suitable for unit/race tests.
- Existing `internal/storage.Store` remains a lower-level event persistence seam. Do not duplicate SQLite setup or create a second SQLite engine in Phase 1.
- A later `SQLiteLedgerRepository` may adapt the existing event store/queued writer after schema, ordering, recovery, redaction, and benchmark gates pass.
- Repository selection is dependency injection/configuration, not a coordinator branch for each backend.
- Repository failure produces an explicit orchestration status; it never silently reports completion.

## State model

```text
created -> queued -> running -> {completed, failed, timed_out, canceled}
queued/running -> cancel_requested -> canceled
failed/timed_out -> retry_pending -> queued
```

Dependency failure produces `blocked`, not `completed`. `cancel_requested` is observable and distinct from terminal `canceled`. A task may publish a terminal event only if its `AttemptID` and expected state/version still match the repository record.

## Implementation steps

### 1. Freeze contracts

Read `AGENTS.md`, `.ai/INDEX.md`, the security/quality/concurrency rules, existing storage files/tests, `internal/subagents/subagents.go`, `internal/runtime/dispatcher.go`, the parent plan, and `docs/architecture/embedded-persistence.md`. Decide exact package ownership and avoid adding a second policy document.

### 2. Add identity and immutable records

Likely location: a focused `internal/orchestration` package or a narrowly justified extension of `internal/subagents`. Define run, task, attempt, dependency, event, and bounded snapshot types. Add server-side display-name allocation with normalization, collision suffixes, deterministic test injection, and run scope. Do not use timestamps alone as identity.

### 3. Add repository and memory implementation

Likely files: `internal/orchestration/ledger.go`, `internal/orchestration/memory_ledger.go`, or an equivalent package with focused tests.

Implement typed errors, immutable snapshots, event idempotency, monotonic sequencing, transition validation, compare-and-set versioning, bounded payload/redaction enforcement, and concurrency protection. Keep the default constructor explicit so callers can inject another repository later. Do not wire SQLite in this phase.

### 4. Add coordinator seam

Implement:

- `Spawn`: validate an immutable task/DAG definition, create run/task records, allocate names, and return a server-issued handle.
- `Inspect`: return a bounded snapshot without mutation.
- `Join`: wait for completion with context cancellation and return final snapshot/results.
- `Cancel`: record `cancel_requested`, cancel in-process contexts, and commit terminal `canceled` only through a valid transition.
- Worker completion: record success/failure only with the current attempt/version.

Use existing bounded worker-pool principles. Child agents cannot recursively delegate. Preserve deterministic dependency ordering and explicit blocked-task behavior.

### 5. Integrate events and projection

Translate coordinator transitions into repository events and update the live projection from those events. Keep TUI/EventBus delivery as a consumer, not the source of truth. Events include run/task/attempt identity, sequence, status, and safe bounded metadata.

### 6. Required tests

- concurrent display-name allocation is unique within a run;
- IDs are immutable and parentage cannot cross runs;
- repository create/get/list returns defensive copies;
- duplicate event/idempotency append is deterministic;
- invalid transitions are rejected;
- compare-and-set rejects stale attempt completion;
- inspect observes queued/running/completed/canceled states;
- join returns on completion or context cancellation;
- cancellation distinguishes `cancel_requested` from `canceled`;
- dependency failure produces `blocked`;
- repository errors never become false completion;
- redaction and size limits reject or scrub sensitive/unbounded payloads;
- fake repository injection proves coordinator does not depend on memory concretions;
- concurrent repository access passes race tests;
- no process farm or recursive delegation path is introduced.

## Acceptance criteria

1. Coordinator depends on `LedgerRepository`, not `MemoryLedgerRepository`.
2. Memory is the explicit built-in default; repository injection is tested with a fake spy.
3. Every task has immutable machine identity, parentage, attempt identity, and a unique generated display name.
4. Live inspect/join/cancel works for in-process runs with bounded contexts.
5. Transitions, idempotency, stale completion, blocked dependencies, redaction, and repository errors are tested.
6. Existing scheduling behavior remains covered; no recursion/process-farm path is introduced.
7. Focused tests and race tests pass; broader gates are recorded separately.
8. Completion explicitly marks durability, restart/recovery, SQLite adapter behavior, benchmarks, and live MCP/API proof as `NOT_RUN`.

## Coordinator review

Source-grounded checks performed after plan creation:

- The repository boundary is intentionally above the existing low-level event store; this avoids coupling the coordinator to SQLite while reusing the existing storage seam later.
- The in-memory backend is explicitly a default data source, not the interface. Acceptance criterion 1 prevents concrete-memory coupling.
- The plan separates live in-process inspection from durable recovery and forbids Phase 1 claims about restart, leases, SQLite, or multi-process behavior.
- Compare-and-set attempt/version checks and distinct cancellation states are required because current Pool/Dispatcher state is transient and has no live query or stale-completion guard.
- Fake-repository injection, defensive copies, typed errors, redaction, and race tests are required to prove the repository pattern rather than only the happy-path coordinator.
- No current source or test evidence justifies adding a model-facing tool, SQLite adapter, REST/MCP surface, or durability claim in this phase.
